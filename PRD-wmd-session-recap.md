## TL;DR

PRD-wmd-memory-writeback stores what each conversation was about under
`wintermute-thread-YYYY-MM-DD`. This PRD reads it back: on
`wm.brain.session.start` (from PRD-wmd-session-boundary), wmd queries
recall for the most recent flushed thread(s) and makes that context
available so the conversation can *continue* — "Earlier you mentioned
your daughter visits Sunday — is that still the plan?" — instead of
greeting a stranger. This is the difference between the per-turn recall
splice that already ships (ad-hoc retrieval keyed on the current
transcript) and genuine cross-session memory (proactive recall of the
last conversation at the moment a new one opens).

## 1. Why this exists

- **Writeback is inert without a reader.** PRD-wmd-memory-writeback fills
  `wintermute-thread-*` subjects; nothing consumes them. This PRD closes
  the loop — store → recall — that makes continuity real.
- **Per-turn recall is not conversational memory.** Today's
  `state.recall.fetch(&turn.transcript)` (daemon.rs:1048) retrieves
  memories *similar to the current utterance*. It cannot surface "what we
  talked about yesterday" unless the user happens to mention the same
  words. Session-recap retrieves the *last thread* by subject, not by
  semantic accident.
- **It's the felt payoff of the whole vision.** A companion that opens
  with "Good morning — yesterday you were worried about the doctor's
  appointment, did it go okay?" is categorically different from one that
  starts cold every time. That sentence is the vision in one line.

## 2. What this builds

### 2.1 Thread retrieval on session start

On `wm.brain.session.start`, query recall (by subject prefix) for:
- today's thread (`thread_subject_for(today)`), if any earlier session
  today was flushed, and
- the most recent prior day's thread.

Use the existing recall query client; filter by `THREAD_SUBJECT_PREFIX`.
Bound to the N most recent thread memories (config `recap_max_memories`,
default 5). A cold store (no threads yet) yields nothing and the session
proceeds exactly as today.

### 2.2 Recap context injection

The retrieved thread memories are held on `DaemonState` for the life of
the session and spliced into the persona/system prompt of that session's
turns — the same mechanism `format_recall_context` + `compose_persona`
already use (daemon.rs:1055-1056), under a distinct, labeled section
("Recent conversations:") so the model can tell standing recall hits from
session-continuity context. This rides the prompt cache like the existing
context splice.

### 2.3 Optional continuity opener

A config flag `recap_opener` (default `false` for v0.1 — conservative):
when enabled and a recent thread was found, on session start wmd proactively
publishes a `wm.brain.reply` that opens with continuity ("Earlier you
mentioned …") *before* the user's first turn, generated by a short model
call from the recap context. Default-off because an unprompted greeting
is a deployment/personality decision (companion.md OQ#4); the
context-injection in 2.2 works regardless and is the safe default.

### 2.4 Self-consistency with writeback

Recap reads exactly the subjects writeback writes (`thread_subject_for`).
The two PRDs share the lib.rs convention; neither invents its own subject.
If writeback wrote proposals (not committed memories), recap must decide
whether to read proposals too — v0.1 reads **committed** thread memories
only (proposals are unreviewed and may be wrong), and notes that until
triage promotes them, recap stays quiet. This keeps recap from surfacing
un-vetted facts to the user.

## 3. Acceptance tests

1. **AC1 — recap injects recent thread context.** With a committed
   `wintermute-thread-<yesterday>` memory in a mocked recall store,
   session.start causes the first turn's request to carry that thread
   text in the system prompt under a "Recent conversations:" label.
2. **AC2 — cold store is a no-op.** With no thread memories, session.start
   proceeds and the first turn's prompt has no recap section; behavior
   matches today.
3. **AC3 — recap is session-scoped.** The recap context is fetched once at
   session.start, not re-queried every turn; assert the thread query
   fires once per session (distinct from the per-turn transcript query,
   which still fires every turn).
4. **AC4 — bound respected.** With `recap_max_memories = 2` and 5 thread
   memories present, at most 2 are injected (most recent first).
5. **AC5 — proposals are not read.** A thread stored only as an unreviewed
   proposal is NOT surfaced by recap (committed-only rule).
6. **AC6 — opener off by default.** With `recap_opener = false`, no
   `wm.brain.reply` is published before the user's first turn.
7. **AC7 — opener on publishes a continuity greeting.** With
   `recap_opener = true` and a recent thread, session.start publishes one
   `wm.brain.reply` referencing the thread, before any turn.user.
8. **AC8 — recall outage tolerated.** Thread query failure logs WARN and
   the session proceeds with no recap; no crash.
9. **AC9 — `cargo test --release --lib` ≥ current+10.**
10. **AC10 — daemon active 60s, NRestarts=0; `cargo deny check bans
    licenses sources` clean.**

## 4. Non-goals

1. **Reading proposals / un-triaged memories.** Committed-only in v0.1.
2. **Cross-day ranging beyond today + most-recent-prior-day.** Vision
   OQ#5; defer.
3. **Personality of the opener.** companion.md OQ#4; the opener is plain
   in v0.1 and default-off.
4. **Summarizing the recap further.** Inject the thread memories as-is;
   re-summarization is a model cost not worth it at v0.1 sizes.

## 5. Open questions

- Should recap prefer episodic thread memories or also pull standing
  profile facts on session start? v0.1: thread memories only (profile
  facts already surface via the per-turn transcript query). Revisit if
  the model misses standing context.
- `recap_opener` default — off for safety, but the companion experience
  may want it on. Flip at deployment, tied to the personality decision.
